조립: 작업은 독립으로 돌리고, 옵션으로 잇는다

RTL review의 다섯 작업(코드 · 검증 상태 · 성능면적 · 합성 · 판단과 plan)은 각자 혼자 돈다. 필요할 때 옵션으로 이어 붙인다. 리뷰어는 고치지 않고, 수정은 늘 다른 task로 나가 따로 검수받는다. milestone에서는 갈래들의 accept된 결과를 블록 sign-off 판정이 모으고, sign-off는 사람이 한다.

여기의 규칙 상당수는 실무에서 확인 · 결정 · 수정할 기본값이다(30_WorkOrders/30_tuning_points.md).

1. 간선 종류 넷과 task 경계

2. RTL review pipeline (A~E)

3. 리뷰 → 자동 수정: 기계가 판정할 수 있을 때만 자동

4. 판정형의 한 척도와 GATE 줄

severity뜻 (코드·검증·성능면적·합성 네 작업이 같은 척도)policy가 계산하는 것
S1 요구 위반지원 config 또는 적법한 사용 순서에서 제품 요구(기능·성능·주파수)를 어긴다확신도 확정·높음이면 차단, 중간·낮음이면 확인 필요(실행할 것과 역할 필수)
S2 위험범위·환경이 바뀌면 어길 수 있다, 또는 어기는지 확인할 수 없다(test되지 않거나 관측되지 않음)LLM이 쓴 확신도는 근거와 대조해 강등: 확정 ⇒ 실행 근거, 높음 ⇒ 도구 사실 + 문서 또는 과거 사례
S3 품질·효율요구는 지키지만 유지보수·style·문서 불일치, 과잉 설계·area 낭비
S4 정보참고
배포 gate는 severity와 따로 센다(copyright 문구·주석의 내부 정보·다른 license 문구·절대 경로 include가 이름이 정해진 배포 대상에 있음). 단계 차단도 따로 센다: 제품 단계(개발 중 · RTL freeze · 배포)별 엄격도 표가 지금 단계에서 차단으로 정한 rule의 열린 지적이다(severity와 차단 칸은 바꾸지 않는다).

5. 억제 기록(waiver · exclusion · 합성 예외)의 수명

6. 블록 sign-off 판정: 갈래의 accept된 결과를 milestone에서 모은다

7. 합성 matrix: 값마다 출처가 있고, 입력이 바뀌면 낡음이 된다

8. 사슬 한 줄: link마다 task가 하나이고, 사이에 사람의 결정이 있다
