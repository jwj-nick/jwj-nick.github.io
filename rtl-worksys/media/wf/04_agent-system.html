workflow agent system: 순서는 코드가, 판단은 LLM이 맡는다

LLM 하나에게 "끝까지 해 줘"라고 맡기면 끝·경계·근거가 흐려진다. 그래서 순서와 멈춤은 결정론 프로그램이 지키고, LLM은 자기 칸의 판단과 작업만 한다. 자율 선언은 글이 아니라 실행 중 허용 목록이다. intake와는 정해진 사건으로만 주고받는다.

여기의 규칙 상당수는 실무에서 확인 · 결정 · 수정할 기본값이다(30_WorkOrders/30_tuning_points.md).

2. intake와 주고받는 사건

방향사건받는 쪽이 하는 일켜는 조건
받음route 블록 + dispatch_ref지금 dispatch_ref와 같고 레코드가 queued일 때만 plan을 시작한다. 레코드 source(출처 · customer_scope · 보는 사람)로 트랙을 덧붙인다늘
받음실행 중 사람의 글(input-to-running)hitl manager가 해석한다. 고객의 답이면 질문 id에 매기고, 조건이 채워진 multi-test를 다시 연다늘
받음위험 고지 · 해제(risk-notice · risk-clear-running)그 내용에 닿는 행동만 즉시 멈추고 안전한 checkpoint는 계속한다늘
받음부모 reject(parent_rejected)on-result로 열린 자식의 STATE에 부모 reject를 적는다. 상태는 바꾸지 않는다늘
보냄후속 요청 · 사슬의 다음 link · 학습 backloginternal 입구로 들어가 gate를 다시 지난다(권한은 새 task의 카테고리로 다시 본다)on-result는 표지를 켠 뒤
보냄학습 완료(learn-done)학습 기록이 확정되면 보낸다. intake가 Track B의 "분류 쪽으로 돌려줄 것"(층 · 질문 결과 · 층을 가른 test · 분류 교정)을 읽어 원장에 track-b 줄을 덧붙인다. 레코드가 닫힌 뒤여도 같다늘(계약 사건)
보냄route 거부(workflow-refused)resolver가 route 결함(트랙이 막는 수정 phase · 맞지 않는 사슬 link)을 찾으면 plan을 시작하지 않고 보낸다. intake가 route를 한 번 다시 계산해 경로가 다르면 새 dispatch, 같거나 두 번째면 논의 대기 + 운영자 알림늘(계약 사건)
보냄실행 중 위험(risk-raised)worker · guard가 올린 위험 고지가 label 자리 없는 고객 레코드에서 일어나면 보낸다. intake가 손잡이 ticket을 확보해 ai:risk와 이유를 두고 레코드의 label 자리를 바꾼다. 레코드 상태는 그대로다표지를 켠 뒤(intake 쪽은 늘 받는다). 그전에는 내부 알림만

방향은 workflow 쪽에서 본 것이다(받음 = intake가 보낸 사건, 보냄 = intake로 보내는 사건). platform 표지는 기본이 꺼짐이고, 시스템 관리자가 켠다(intake 쪽 짝 설정이 있으면 함께 켠다). 켜기 전에는 더 보수적인 동작(제안만, 질문하고 기다림, 내부 알림)을 한다.
