KB 만들기와 유지: 단계마다 무엇이 들어가고, 누가 무엇을 내놓나

한 장 해설이 시스템의 부품과 고리를 보였다면, 이 페이지는 시간 순서로 따라간다. 제품 하나의 KB를 처음 만들 때(B0~B7)와 그 뒤 계속 유지할 때(사건 · 매일 · 정기 · 질문), 단계마다 무엇이 들어가고 누가 처리해 무엇이 나오며 사람은 어디서 확인하는지를 같은 모양의 그림으로 보인다.

1전체 지도: 처음 한 번, 그다음 계속

처음 만들기 (Bootstrap): 제품 하나를 한 번 채운다
B0 준비repo · 규칙 · 도구 · CI
B1 조사원천 목록 · card
B2 릴리즈 축과거 릴리즈 재구성
B3 bug영향 · 수정 릴리즈
B4 요구 · spec어긋난 곳 표시
B5 module생성 표 + 서술
B6 나머지구조 · 검증 · 구현
B7 고객보안 준비 뒤

릴리즈 축(B2)을 먼저 세우는 이유: bug의 "영향 받은 릴리즈"와 고객의 "가진 릴리즈"가 모두 릴리즈 기록을 가리키기 때문이다. 끝은 질문 표본으로 잰다(답한 비율 · gap · hard-zero).

계속 유지 (Operate): 그 뒤로 네 가지 박자로 돈다

사건마다

commit · bug 종료 · 요구 변경 · release tag · 납품 · 고객 답변 · 합성 run · 리뷰 판정 · task 완료 · 원천 이동 → 확인 · 갱신 제안 MR

매일

lint 전체 → 지도 다시 만들기(stale · 충돌 · 문서 필요 · gap 순위 · 확정 뒤 영향)

정기

Curator 정리(충돌 · FAQ · 중복 · 은퇴 · gap 순위 → 작업), 질문 표본 채점, 정본 회의

질문할 때

Librarian의 답, 답하지 못한 자리(gap) → 지도 → 작업

2한 단계의 공통 모양

처음 만들 때든 유지할 때든, agent가 일하는 단계는 모두 같은 여섯 칸을 지난다. 아래 3장과 5장의 표는 이 여섯 칸을 단계마다 채운 것이다.

1작업
종류 · 대상 · 고객 권한 · 찾아볼 원천 목록 · 판정 등급 · 중복 방지 key
2규칙 · 틀
문서 종류의 template(필수 절 · 절마다 쓸 것), 출처 우선순위, 문서 기준
3agent 세션
원천(전처리본)을 읽고 초안. 사실마다 [s1], 추론은 근거와 함께, 모르면 "모름"
4MR
draft 문서 + 제안 머리(사람이 꼭 볼 곳 · 판정 등급 · 근거 원천)
5검사 · 판정
lint가 바뀐 문서를 판정, Curator가 다섯 줄 요약, 담당이 판정 → 확인 기록 + 본문 hash
6지도
merge 뒤 매일 lint가 채움 상태 · stale · gap 순위를 다시 만든다 → 다음 작업

  • 인터뷰 시트: 역할마다 한 장, 항목마다 가설 · 다른 답 후보 · 답이 바꾸는 것
  • 기대 자료 목록: 원칙상 있어야 하는데 없는 자료, 채울 길, 채워지면 오는 사건
사람 · 지도담당이 시트에 맞음 · 고침 · 모름으로 답하고(답은 원천 종류 interview로 남는다), 제품 리더가 card를 확인한다. 답하지 못한 것은 card의 빈 곳으로. 지도에 제품 행이 생기고, 원천만 있는 칸은 source-only
B2 릴리즈 축Release recorder kb-release-record
입력

  • 릴리즈 note · 납품 폴더

처리과거 릴리즈를 같은 형식으로 재구성한다. 못 찾은 칸은 "없음" · "모름". 줄기(trunk · maintenance)를 적고 같은 줄기끼리만 잇는다
출력MR:
  • 릴리즈마다 release 기록(+ checklist 판정)
  • "앞으로 반드시 남길 기록" 목록
사람 · 지도릴리즈 담당이 확인 → 확정 → hash가 원장에. 지도의 release 칸이 reviewed
B3 bugHarvester kb-harvest + 포함 여부 계산
입력

  • 수정 commit
  • 포함 여부 계산 결과(script)
  • 문서 기준
처리문서 기준에 걸리는 bug만 문서로 쓴다(고객 · FPGA 발견, 릴리즈 뒤 발견, 공유 module, spec 오독 등). 영향 · 수정 릴리즈는 계산 결과에 (계산: ancestry)
출력MR:
  • bug 문서: 재현 조건 · 원인 · 수정 · 영향 범위 · 교훈
  • bug 목록(생성, 나머지는 한 줄)

B4 요구 · specHarvester

출력MR:

  • spec 목록

처음 만들기가 끝났다는 판정

card와 핵심 문서 종류가 reviewed, lint 오류 0, 실제 질문 표본을 KB만으로 답하게 했을 때 답한 비율 [ ] 이상(목표는 팀 리더), hard-zero 0. 이때 사건 hook을 켜고(5장), 사람 없이 받아들일 제안 종류(auto)를 정한다.

4지도가 채워지는 모습 (가상 제품 하나)

진척은 지도(_map/coverage.md)로 보인다. 칸의 상태는 다섯이다: none 원천도 문서도 없음 · source-only 원천만 있음 · draft agent가 씀 · reviewed 사람이 확인 · stale 원천이 바뀜.

B1 조사 뒤

cardreleasebug요구specmodule구조검증구현고객

B2 · B3 뒤

cardreleasebug 3/5요구specmodule구조검증구현고객

B4 · B5 뒤

cardreleasebug요구spec 충돌 1module 2/3구조검증구현고객

B6 뒤 · 유지 중

cardreleasebug요구specmodule stale 1구조검증구현고객

마지막 칸의 stale 1은 실패가 아니라 시스템이 살아 있다는 표시다: 코드가 바뀌었고, 그 module 문서를 다시 보라는 제안이 이미 와 있다. 고객 칸은 고객 단계를 열기 전까지 none이다.

5계속 유지: 사건마다의 입력과 출력

원천에서 사건이 생기면 event router가 작업을 만들어 나눈다. script가 할 수 있는 것은 script가 하고(지도 표시), 판단이 필요한 것만 agent 작업이 되어 MR로 온다. 담당에게는 하루 한 묶음으로 간다.

7문서 한 장의 일생

문서의 상태는 다섯 가지 가운데 하나다. 사람이 쓰는 칸은 status(draft · reviewed · retired)뿐이고, stale과 outdated는 lint가 계산해 지도에 보인다.

source-only
원천은 있고 문서는 없다. 지도의 빈 칸 = 채울 일
draft
agent가 쓴 초안. 답에 쓰이면 "draft 근거" 표시
reviewed
사람이 확인했다. 누가 · 언제 · 어떤 방법으로 · 어떤 본문(hash)
stale · outdated
원천이 바뀌었다 · 확인 뒤 본문이 바뀌었다. 다시 볼 일
retired
원천이 사라졌거나 더 쓰이지 않는다. 지우지 않고 은퇴
source-only → draft: 작업 → agent 초안 MR
draft → reviewed: 담당이 판정하고 확인 hash를 찍는다
reviewed → stale: 원천 revision이 바뀐다(lint가 계산)
stale → reviewed: "그대로 참" 제안을 받아들인다(revision만 오른다)
stale → draft 수정 → reviewed: "갱신" MR을 판정한다
reviewed → outdated: 확인 뒤 본문이 바뀌었다 → 다시 판정
아무 상태 → retired: Curator 제안, 사람 승인
기록형(릴리즈 · 납품): draft → 확정 → 원장 hash. 그 뒤로는 사후 정정만 덧붙인다

개인 KB에서도 모양은 같다. 사람이 한 명이므로 판정을 가볍게 두고(한 번 읽음), 원천은 내 노트 repo의 commit이다.
