설계 해설 · 모든 예시(제품 · 고객 · 수치)는 가상 · 숫자 기준은 공란

KB Agent System: 질문하면 근거와 함께 답하는 지식 저장소를, 전용 agent들이 짓고 유지한다

흩어진 제품 자료(코드 · spec · issue · 릴리즈 · 합성 결과 · 고객 질문)를 사람과 AI agent가 실제 질문에 답할 수 있는 하나의 KB로 만들고, 원천이 바뀌어도 낡지 않게 유지하는 시스템이다. 이 페이지 하나만 읽고도 시스템 전체가 이해되도록 썼다. 순서대로 읽으면 무엇을(1~2) → 누가(3~4) → 어떻게 돌아가나(5~6) → 무엇이 믿게 하나(7~8) → 어떻게 세우나(9~11) 순서다.

KB를 구축할 때 KB 전용 agent system이 KB를 짓는가?
맞다. 사람은 문서를 쓰지 않고 판정한다.

agent 다섯이 원천을 읽어 문서 초안과 갱신을 MR(merge request)로 낸다. script 셋이 검사 · 계산 · 작업 분배를 맡는다. 사람은 MR을 보고 받아들일지 정하고, 받아들인 문서만 reviewed가 된다. 사람이 직접 쓰는 것은 판정 기록, 릴리즈 확정, agent가 찾지 못한 몇 가지 사실(예: 담당 역할)뿐이다.

agent: 쓴다(제안)

원천을 읽고 template대로 초안을 쓴다. 모든 쓰기는 MR이고 draft로 시작한다.

script: 센다 · 막는다 · 나눈다

신선도 · 연결 · 누출 · 확정 기록 변조 · 생성 칸을 판정하고, 할 일을 작업으로 만들어 agent에 나눈다. LLM을 부르지 않는다.

사람: 판정한다

MR을 받아들이면 누가 · 언제 · 어떤 방법으로 확인했는지와 확인한 본문의 hash가 남는다.

1북극성: 무엇을 만드나

어떤 제품의 어떤 질문이든, 사람과 agent가 KB에서 근거(원천 위치와 버전)가 붙은 답을 찾는다. 답을 못 찾으면, 그 빈 곳이 자동으로 채울 일이 된다.

믿을 수 있다

모든 사실에 출처와 버전이 붙고, 사람이 무엇을 확인했는지 보인다. 장치: 인용 [s1], 근거가 붙은 추정 표시, 확인 기록과 확인한 본문의 hash.

살아 있다

원천이 바뀌면 KB가 스스로 "다시 봐야 함(stale)"을 표시하고, 갱신 제안이 자동으로 온다. 장치: 문서마다 원천 revision, 매일 lint, 사건 hook.

빈 곳이 보인다

무엇이 없는지, 어떤 질문에 답하지 못했는지가 목록으로 남는다. 장치: 지도(_map/), 답하지 못한 질문의 기록(gap)과 순위.

왜 문서 모음이 아니라 "시스템"인가

자료를 한 번 모아 정리하면 네 가지가 무너진다. 각각을 막는 장치가 시스템의 부품이 된다.

무너지는 것막는 방법
낡는다. 정리한 날부터 코드와 문서가 갈라진다모든 사실이 원천 revision을 든다. 원천이 바뀌면 lint가 stale을 표시하고 agent가 갱신을 제안한다
출처가 사라진다. 옮겨 적은 숫자와 문장은 어디서 왔는지 모르게 된다복사하지 않고 가리킨다. 숫자는 원래 자리(QoR matrix · 결과 서버)에만 있고 문서는 run id를 가리킨다
고객 정보가 섞인다. 한 고객의 질문 · 요구가 다른 고객에게 가는 답에 들어간다고객 정보는 처음부터 별도 repo에 두고, 이름 · 내용 · 채널 · 세션 · 로그에서 막는다(8장)
채워지지 않는다. 한 번의 정리 뒤에는 아무도 채우지 않는다채우는 일을 원천 사건(commit · ticket 종료 · 릴리즈)에 붙이고, 답하지 못한 질문이 채울 일의 순위가 된다

2한 장 그림

원천은 읽기만 한다. KB agent system이 원천을 읽어 KB repo를 채우고 유지한다. 사람과 다른 agent는 KB에 묻는다. 사람은 그 가운데에서 판정한다.

3부품: 이것이 전부다

3.1 agent 다섯 (LLM)

agent는 모두 Claude Code의 subagent + skill로 선다. 사람이 대화로 부르거나, event router가 비대화형 세션으로 연다. 공통 규칙이 있다: 원천은 읽기만, KB에는 MR로만, 입력으로 받은 고객 권한 밖은 읽지 않는다.

3.2 script 셋 (LLM 없음, 결정론)

lint bot

문서 모양 · 원천 존재와 신선도 · 인용과 추정 근거 · 연결 · 고객 이름 · 확정 기록 변조 · 생성 칸을 검사하고 지도(_map/)를 만든다. 문서를 고치지 않고, 자기 메시지로 고객 정보를 흘리지 않는다. MR마다 바뀐 문서만, 매일 전체.

generator

코드에서 port · parameter 표와 module 목록을 만든다(사람이 손으로 쓰지 않는다). 릴리즈 확정 순간의 표를 굳히고 hash를 원장에 남긴다. 사람이 판정할 때 확인한 본문의 hash를 찍는다.

event router · scheduler

원천 사건 · 지도의 빈 곳 · 정기 일정 · 사람 요청을 작업으로 만들어 agent 세션에 나눈다. 작업마다 고객 권한과 찾아볼 원천을 붙이고, 이미 거절된 제안은 다시 보내지 않는다.

3.3 규칙과 계약

규칙 _schema (KB repo 안의 정본)

  • 문서 종류 29: 종류마다 자리 · id 모양 · 필수 필드 · 필수 절 · 절마다 쓸 것. template은 여기서 생성한다
  • 연결 18종: 한 방향으로만 쓰고, 역방향은 lint가 만든다
  • 출처 우선순위: 사실 종류(structure · intent · number · history · practice)마다 무엇을 먼저 믿나
  • 질문 유형 15: 질문마다 KB를 여는 길
  • 사건 표 12: 원천 사건 → script 동작 · agent 작업
  • checklist: 릴리즈 · 검증 항목과 자동 판정 여부

계약 11 (JSON Schema)

  • 문서 머리(front matter)
  • registry 넷: 제품 · 원천 · 고객 정책 · 담당 역할
  • 고객 이름 목록
  • 작업: agent 세션 하나의 입력
  • 답 · gap(답하지 못한 자리) · 제안(MR 머리) · lint 결과

agent의 입력과 출력이 계약을 벗어나면 script가 거절한다.

4사람의 자리: 쓰지 않고 판정한다

역할하는 일
KB 관리자규칙(_schema)과 registry의 정본 관리, 정본 회의, 매일 지도 점검과 작업 배분. 이 역할이 비면 시스템은 조용히 낡는다.
제품 리더제품 card와 구조 문서 확인, 파일럿 착수 결정
문서 담당(sub-top · 검증 · 구현)자기 범위 MR 판정(reviewed로 올림), 충돌 판정
릴리즈 담당checklist의 사람 항목 판정, 예외 승인, 릴리즈 확정
FAE고객 repo(질문 · feedback · 납품 확인), 새 고객을 이름 목록에 등록
보안 담당고객 repo 권한, 원천별 AI 읽기 허용, 전처리 규칙, 고객 ID 정책
팀 리더질문 표본과 품질 목표, 단계 전환, 판정 등급 기본값

판정 등급으로 사람의 부담을 조절한다. auto 생성 칸을 다시 만든 것처럼 script가 증명한 것은 사람 없이 merge한다. light 사실 추가는 한 사람이 읽는다. full 구조 · 영향 판단은 담당이 원천과 대조한다. 확인 방법은 실제로 한 것만 적는다: 사람이 읽음 · 사람이 코드와 대조 · script가 증명. agent가 한 대조를 사람의 대조로 적지 않는다.

5작업 한 건이 도는 고리: 시스템의 심장

세 흐름(처음 채우기 · 유지 · 질문)은 사실 하나의 고리다. 모든 agent 세션은 작업 한 건에서 시작하고, 결과는 MR 하나다. 작업은 네 곳에서 생긴다.

① 작업이 생긴다bootstrap 계획 · 원천 사건 · 지도의 빈 곳 · 사람 요청
② router가 작업을 만든다종류 · 대상 · 고객 권한 · 찾아볼 원천 · 판정 등급 · 중복 방지 key
③ agent 세션 하나skill이 규칙과 template을 들고 원천을 읽는다
④ MRdraft 문서 + 제안 머리(사람이 볼 곳 · 등급)
⑤ 검사lint가 바뀐 문서를 판정, Curator가 다섯 줄 요약
⑥ 사람 판정받아들이면 확인 기록 + 본문 hash → reviewed
⑦ 지도매일 lint가 채움 상태 · stale · gap 순위를 다시 만든다
↺ 지도의 빈 곳(없는 문서 · 다시 봐야 할 문서 · 답하지 못한 질문)이 다시 ①의 작업이 된다. KB가 스스로 다음 할 일을 만든다.

작업 한 건의 모양 (계약 kb_job)

id: J-0002
kind: sync                 # survey · harvest · sync · curate · faq · release-record …
origin: event              # bootstrap-plan · event · map · schedule · human
event: issue-closed-bug jira:VXD-130
skill: kb-sync
target: { product: vx-dec, doc_type: bug, doc_ids: [BUG-VXD-130] }
customer_scope: none       # none 또는 고객 하나. all은 없다
sources: [jira:VXD-130, svn-main:/commit/r1502]
review_level_hint: full
dedupe_key: BUG-VXD-130@r1502

이 모양이 지키는 것

  • 범위: agent는 받은 원천 목록 밖을 찾아본 것처럼 쓰지 않는다. 그래서 "없음(찾아본 곳: …)"이 믿을 만하다.
  • 고객 권한: 작업 하나는 고객 하나까지만 본다. 두 고객을 한 세션에서 보지 않는다.
  • 반복 방지: 같은 대상 · 같은 원천 revision으로 거절된 제안은 다시 작업이 되지 않는다.
  • 기록: 작업 로그는 권한 단위로 남는다(고객 작업은 그 고객 폴더에).
  • 예외: Librarian은 작업이 아니라 질문으로 불린다. 답하지 못한 자리가 지도를 거쳐 작업이 된다.

6세 흐름을 시간 순서로 (가상 제품 family VX로)

6.1 Bootstrap: 제품 하나를 처음 채운다

릴리즈 축을 먼저 세운다. 그래야 bug의 "영향 받은 릴리즈"와 고객의 "가진 릴리즈"를 가리킬 수 있다.

1 조사Surveyor → registry · card · 빈 곳 질문. 제품 리더가 확인
2 릴리즈 축Release recorder가 과거 릴리즈 재구성. 못 찾은 칸은 없음 · 모름
3 bug종료된 bug부터. 영향 릴리즈는 기록이 없으면 VCS로 계산
4 요구 · specspec 목록, 코드와 어긋난 곳(spec-gaps)
5 modulesub-top마다. port · parameter 표는 코드에서 생성
6 고객보안 준비(이름 목록 · 전처리 · 권한)가 끝난 뒤
7 나머지architecture · verification · implementation …

단계마다 Harvester가 MR을 내고, 담당이 판정하고, lint가 지도를 갱신한다. 지도의 빈 칸이 줄어드는 것이 진척이다.

6.2 Operate: 원천에서 사건이 생길 때마다

예: bug ticket VXD-130이 종료되었다.

사건issue tracker hook → router: issue-closed-bug
작업router가 작업을 만든다. ticket의 고객 tag로 고객 권한, registry로 원천 목록
Harvesterticket(고객 이름을 CUST-ID로 바꾼 전처리본)과 수정 commit을 읽어 bug 문서 초안
계산 · 표시영향 릴리즈는 script가 계산 → (계산: ancestry). 다음 tag 전이면 fixed-in = 미정
함께 온 사건같은 commit으로 module 원천이 바뀜 → module 확인 제안도 같은 MR에
판정sub-top 담당이 MR 판정 → reviewed

사건이 몰리면 문서 단위로 묶고, 담당에게는 하루 한 묶음으로 확인을 요청한다(상한은 팀 리더가 정한다). 교훈은 RTL review의 bug 패턴 library로 넘긴다.

6.3 Use: 질문할 때

신입: "blk_parse의 header FIFO 깊이는?"

Librarian이 질문 유형을 고르고 module 목록 → vx-dec/mod/blk_parse를 연다. port · parameter 표는 코드에서 생성한 칸이라 코드 값 16이 있다. 그런데 spec-gaps에 열린 충돌(uarch spec은 32)이 있다.

답: "코드 값은 16이고 spec은 32다. 담당이 판정 중이다." 여기에 conflict 표시가 붙고, 인용은 문서 id와 원천 revision이다.

FAE(고객 CUST-001 권한): "이 고객이 쓰는 릴리즈에 AXI burst bug가 있나?"

CUST-001 폴더의 납품 기록 → 지금 쓰는 릴리즈 2.0 → bug 문서의 fixed-in(2.0)을 따라간다. 답: "없다. 이전 납품 1.1에는 있었다."

고객 권한이 없는 사람이 같은 질문을 하면, 고객이 가진 릴리즈는 말하지 않고 "권한 밖" gap을 남긴다. 다른 고객이 있다는 사실은 어느 경우에도 드러나지 않는다.

답의 모양결론 한두 문장
근거주장마다 문서 id@revision
표시draft 근거 · stale · 추정 · 계산 · 충돌을 그대로 옮긴다
못 찾은 곳gap: 이유(문서 없음 · 절 없음 · 연결 없음 · 권한 밖 …) + 자리 → 지도 → 작업

7무엇이 믿게 하나

7.1 문서 한 장의 해부

머리 (agent와 script가 읽는 구조)

id: BUG-VXD-117            # 원천 ID를 그대로
type: bug
status: reviewed           # draft | reviewed | retired
sensitivity: customer-derived
owner_role: sub-top 담당    # 사람 이름이 아니라 역할
applies_to: { releases: [REL-vx-dec-1.0, REL-vx-dec-1.1] }
sources:                   # 복사하지 않고 가리킨다
  - { key: s1, kind: issue, ref: "jira:VXD-117", rev: "2026-06-02" }
  - { key: s2, kind: vcs-log, ref: "svn-main:/commit/r1431", rev: "r1431" }
verified: { by_role: sub-top 담당, date: 2026-06-05,
            method: human-read, body_hash: "…" }   # 사람만
links:                     # 한 방향만. 역방향은 lint가
  - { rel: caused-by, to: vx-dec/mod/blk_filter }

본문 (사람이 읽는 설명)

## 요약
특정 config에서 filter 경계 처리가 틀린다 [s1].

## 수정
경계 조건을 고쳤다 [s2].

## 영향 범위
1.0과 1.1이 영향을 받는다 (계산: ancestry).
그 이전 릴리즈는 모름: 버그를 넣은 commit을
아직 찾지 못했다.

모든 문서는 ## 요약으로 시작하고, 종류별 필수 절이 이어진다. 쓸 것이 없어도 절을 지우지 않는다.

7.2 다섯 가지 표시: 모르는 것을 모른다고 쓴다

표시뜻지키는 장치
[s1]원천 s1에 있는 사실lint: 인용한 key가 원천 목록에 있어야 한다
(추정: s2 — 이유)원천 s2에서 추론한 사실lint: 근거 key가 없는 추정은 오류. 근거가 없으면 "모름"으로 쓴다
(계산: 규칙)script가 규칙으로 계산한 사실(예: VCS 조상 관계)포함 여부는 script의 결과만 쓴다
없음(찾아본 곳: …)찾아보았지만 없다. 빈 칸(찾아보지 않음)과 다르다찾아본 곳은 작업이 준 원천 목록 안이어야 한다
모름: 이유있을 수 있으나 확인할 수 없다답에서는 partial + gap이 된다

7.3 낡음 · 확인 · 확정

stale: 원천이 바뀌었다

문서가 본 revision과 원천의 현재 revision이 다르면 lint가 지도에 올린다. 문서에는 쓰지 않는다(계산한다). 생성 칸만 쓰는 원천이면 script가 확인하고, 나머지는 사람이 확인한다.

reviewed-outdated: 확인 뒤 바뀌었다

사람이 판정할 때 확인한 본문의 hash가 남는다. 그 뒤 본문이 바뀌면 lint가 짚고, 답에서는 draft처럼 다룬다.

확정 기록: 바뀌지 않는다

릴리즈가 확정되면 그 순간의 "고친 bug · 알려진 issue" 표가 굳고, hash가 보호 원장에 남는다. 나중에 안 사실은 "사후 정정"으로 덧붙이기만 한다. 고객에게 낸 수치는 동결 사본으로 둔다.

7.4 자료끼리 다를 때

충돌은 지우지 않고 기록한다. 먼저 사실의 종류를 고르고, 종류마다 다른 순서로 적을 값을 고른다. "코드가 늘 이긴다"가 아니다.

사실 종류예먼저 믿는 것
structureport · parameter · 계층생성 원천 → 코드 → 문서. 코드와 spec이 다르면 늘 spec-gaps에 올린다
intent기능 · 요구 · 규격spec → 요구 기록 → 결정. 어느 쪽이 맞는지는 담당이 판정한다
number합성 결과 · coverage원래 자리(record)만. 문서의 숫자는 인용이어야 한다
history릴리즈 · bug 이력확정 기록 → issue → log
practice사용법 · 주의점reviewed KB → tool 문서 → wiki

7.5 hard-zero 넷: 하나라도 나오면 변경을 되돌린다

근거 없는 사실

인용 없는 주장이 답이나 문서에 들어갔다.

고객 정보 누출

권한 밖 고객의 이름 · id · 내용이 보였다.

확정 기록 훼손

확정된 릴리즈 · 납품 기록이 바뀌었다.

낡음 은폐

원천이 바뀌었는데 허용 지연 밖까지 표시가 없었다.

8고객 정보를 지키는 여섯 방향 (회사 KB)

고객 정보는 이름만의 문제가 아니다. 저장 위치를 처음부터 나누고, 한 겹이 뚫려도 다음 겹이 막도록 이름 · 원천 읽기 · 내용 · 채널 · 세션 · 로그의 여섯 방향에서 막는다. 개인 KB에서는 같은 장치가 "회사 정보 차단"과 "공개 · 비공개 구분"이 된다(9장).

방향장치
바탕: 저장 위치고객 정보는 처음부터 고객 repo에, 고객 단위 권한(폴더 권한이 안 되는 Git 서버에서는 고객마다 project). 검색 index도 권한 단위로 따로
이름고객 이름 · 다른 표기 · 과제명 · 메일 domain은 이름 목록에만. lint가 본 KB · 지도 · 로그 · registry를 검사한다
원천 읽기고객 이름이 섞인 원천은 전처리(이름 → CUST-ID) 뒤에만 agent가 읽는다. 새 고객은 등록 전까지 읽지 않는다
내용고객에게서 온 내용은 sensitivity로 표시하고, 고객에게 나가는 답(outbound)에는 인용하지 않는다
채널lint 메시지에 이름을 쓰지 않는다(목록 번호만). commit message · MR 제목 · branch 이름도 push 때 검사한다
세션모든 agent가 고객 권한을 입력으로 받고, 한 세션은 고객 하나까지만. 여러 고객의 같은 질문은 두 단계로만 FAQ가 된다(고객 세션은 질문의 서명만 남기고, 고객 권한 없는 세션이 본 KB 원천만으로 쓴다)
로그답하지 못한 질문 기록은 누출 검사 뒤 권한 단위 로그에. 본 KB 로그에는 질문 원문이 없다. 잘못 들어간 줄은 보안 담당이 지우는 절차가 있다

9세 층: 같은 엔진으로 회사 KB와 개인 KB를 만든다

시스템은 세 층으로 나뉜다. 엔진은 어디서나 같다. 규칙 묶음(어떤 문서를 어떤 모양으로 두나)이 영역을 정하고, 인스턴스(실제 원천과 문서)가 KB 하나가 된다. lint · template · 지도는 규칙 묶음을 읽어 움직이므로, 규칙 묶음을 바꾸면 같은 엔진이 다른 영역의 KB를 짓는다.

회사 KB
개인 KB
엔진어디서나 같다
원칙 여덟 · agent 다섯의 역할 · script 셋(lint · generator · router) · 계약 11 · 시험 runner. 작업 → MR → 판정 → 지도의 고리. 인용 · 추정 · 모름 표시, stale, 확인 hash.
규칙 묶음_schema: 영역을 정한다
RTL IP 제품 KB: 문서 종류 29(card · module · bug · 요구 · 릴리즈 · 납품 …), 연결 18, 릴리즈 축과 확정 원장, 고객 repo와 여섯 방향 분리
공부 · 업무 노트 KB(예): workspace card · 주제 · 자료 노트(논문 · 책) · 결정 · 내가 물었던 질문. 릴리즈 축과 고객 repo 없음
인스턴스registry · adapter · 문서

회사 KB의 장치개인 KB에서는

릴리즈 축 · 확정 원장 · 고객 repo쓰지 않는다(필요해지면 나중에)

확인한 것: 문서 종류 셋짜리 개인용 규칙 묶음과 실제 git 원천을 같은 엔진에 붙였을 때 오류 0, 원천 노트를 고쳐 commit하면 stale, 근거 없는 추정과 없는 연결은 오류, 지도의 열은 개인용 문서 종류로 나왔다.

10실제 KB를 만드는 과정: 회사용과 개인용

설계 워크스페이스에서 만든 것은 일반화한 규칙과 가상 제품으로 시험한 엔진이다. 여기서 두 갈래로 실제 KB가 나온다. 두 갈래 모두 엔진은 복사하고, 규칙 묶음과 인스턴스를 채운다.

10.1 회사로 가져갈 묶음과 회사 KB

① 설계 · 가상 시험일반화한 규칙, 가상 제품 family로 lint · agent 시험 (지금 여기)
② 회사 현실 대비가져가기 전: SVN adapter · 조상 관계 계산, 원천 전처리, 작업 분배 reference, CI 예시, 회사 첫 주 작업 지시서
③ packing내부 파일(진행판 · 옛 판 · 시험 원 출력) 제외, 금지 표기 검사
④ 셋업빈 KB project, _schema · _tools 복사, registry, lint CI
⑤ adapterSVN · issue tracker · wiki. 합격 = 이 묶음의 시험 사례와 같은 결과
⑥ 파일럿제품 하나: 조사 → 릴리즈 축 → 초안 → 판정 → kb-ask를 사람에게
⑦ 넓히기다음 제품은 card부터, 파생 제품은 차이만

셋업 명령 (빈 폴더에서 첫 lint까지, 실제로 따라 해 확인)

git clone <KB project> kb && cd kb
cp -r <묶음>/40_schema _schema
cp -r <묶음>/20_contracts _schema/contracts
cp -r <묶음>/55_tools _tools
# _registry/ 네 파일: 제품 · 원천 · 고객 정책 · 역할
git clone <코드 project> ../src/code
python _tools/kb_template.py --schema _schema --out _schema/templates
mkdir -p products/<family>/<product>
cp _schema/templates/card.md products/<family>/<product>/card.md
python _tools/kb_lint.py --kb . --schema _schema \
  --contracts _schema/contracts --sources ../src --out _map

채우지 않은 card에는 오류 7건이 채울 곳을 가리키고, 채우면 오류 0이 되며 지도가 생긴다.

회사에서 먼저 확인할 것

  • 고객 repo의 권한 단위: 고객 폴더 단위가 되는가, 안 되면 고객마다 project
  • VCS 조상 관계를 script가 물을 수 있는가(SVN mergeinfo · git ancestor)
  • 릴리즈 · 검증 checklist의 실제 항목과 자동 판정 여부
  • 원천 전처리(고객 이름 → CUST-ID)를 어디서 하나
  • kb-ask를 다른 agent에 여는 방식, 작업의 고객 tag를 넘기는 방식

첫 단계의 기본안: 고객 정보는 다루지 않고 시작한다. 이름 목록 · 전처리 · 고객 repo 권한이 준비되면 연다.

10.2 개인 KB

① 새 워크스페이스private git. 회사 워크스페이스와 섞지 않는다
② 엔진 복사_tools · 계약. 고치지 않고 그대로
③ 규칙 묶음 쓰기문서 종류 · 연결 · 원천 종류(논문 · 책 · 웹 · 세션 로그) · 지도 열
④ registry내 repo들(rev_resolver: git), 읽기 금지 원천, 회사 정보 차단 목록
